# 用户反馈与项目经验召回设计

日期：2026-09-22。状态：方案已确认，尚未实现。

本文记录本轮讨论的产品边界、数据契约和实施计划。除文中明确标为当前已有的提示词组装能力外，反馈、经验和新任务设计均未实现。

## 1. 目标与已确认边界

在现有“禅道 → 云端 → 本地 Worker → 源码调查 → 飞书通知”流程上，增加用户反馈、经验提炼和按需召回，使已确认的调查教训能影响后续分析，并可追溯其来源和效果。

- 云端运行 `code/`，负责反馈接收、持久化、任务派发和通知。
- 本地工作电脑运行 `worker/`，主动领取绑定项目的任务，不需要云端连接本地。
- 经验保存在 `REPO_PATH` 指向的业务仓库，与该项目的技能和文档关联；不默认保存在 Bug Bot 仓库。
- 只有经人工确认的经验进入正式召回。第一版在本地确认，不建设云端审核界面。
- 系统可建议补项目文档或修改模块 Skill，但只在通知中说明建议和依据。相关修改由人工完成，系统不自动修改这些文件。
- 功能默认开启，通过环境变量关闭；关闭不删除已有文件，不影响普通 Bug 分析。
- 第一版使用文本文件与确定性检索，不引入向量数据库或额外的多 Agent 编排。
- Git 跟踪策略单独决定；本方案不自动修改业务仓库的 `.gitignore`，不自动提交或推送。

## 2. 当前实现与新增责任

当前 Worker 已有规则分诊、Agent CLI 执行、结果解析、超时和 Provider 失败回退。云端任务队列为内存存储；分析结果通过回调发送通知。当前没有本文定义的反馈卡片、持久反馈、经验文件和检索注入流程。

现有分析结果中的 `resolved` 是模型对根因明确程度的判断，不等于修复或人工验证。不得直接用该字段确认经验正确。

新增责任划分：

| 组件 | 责任 |
| --- | --- |
| 云端 | 验证反馈来源，保存原始反馈与分析快照，可靠派发项目任务，发送处理结果 |
| Worker 固定程序 | 验证任务，记录代码版本，保存原始材料，检索经验，校验模型输出并写文件，回报处理状态 |
| 调查 Agent | 结合候选经验检查当前代码，给出结论及经验使用记录 |
| 经验提炼 Agent 调用 | 根据反馈、原分析和证据生成候选经验或人工维护建议 |
| 人工 | 判断候选经验是否成立，确认、修订或拒绝；自行修改项目文档和 Skill |

云端下发结构化数据，不下发可执行脚本、任意命令或本地目标路径。

## 3. 主流程

```text
分析完成 → 保存分析快照 → 飞书结果通知及反馈卡片
                                  ↓
                            用户评价并补充原因
                                  ↓
                    云端保存反馈和 feedback.process 任务
                                  ↓
                       绑定项目的 Worker 领取
                                  ↓
                     固定程序幂等保存原始反馈
                                  ↓
             开关与反馈资格检查 → 提炼候选经验或维护建议
                                  ↓
                      回报结果 → 云端通知用户
                                  ↓
                       人工在本地确认候选经验
                                  ↓
                       正式经验文件及索引更新
                                  ↓
                 后续分析前固定检索 → 注入摘要与路径
```

反馈已保存、候选已生成和经验已生效是不同阶段，通知不得混称为“已学习”。

## 4. 反馈入口与权限

结果通知附反馈卡片，评价选项为：

| 评价 | 补充要求 | 默认后续行为 |
| --- | --- | --- |
| 正确 `correct` | 原因可选，可附验证证据 | 保存为质量反馈，不自动新增成功经验 |
| 部分正确 `partially_correct` | 必填错误或遗漏部分 | 在功能开启时进入候选提炼 |
| 错误 `incorrect` | 必填原因；可附实际根因和修复证据 | 在功能开启时进入候选提炼 |
| 无法确认 `unverifiable` | 必选原因类别，允许说明未知 | 证据不足时仅记录，不强行提炼 |

原因类别至少区分：Bug 描述缺失复现条件、Agent 漏查已有信息、缺少验证证据、其他。合理返回 `inconclusive` 不自动算判断错误。

默认允许目标项目配置群内能访问卡片的成员反馈。云端验证平台事件真实性和卡片与项目、原任务的关联，记录真实反馈人身份；具体平台校验与卡片协议在实施时查官方文档确认，不在本文假定接口细节。

允许追加和更正反馈，不覆盖历史；更正通过 `supersedesFeedbackId` 关联旧记录。多人反馈冲突时保留各方意见，标记待确认，不按最新一条自动得出最终事实。纯重复的平台投递不算新增反馈。

## 5. 数据契约与状态

以下是逻辑字段，具体 TypeScript 定义和接口路径在实施阶段确定。

### 5.1 分析快照

每次分析至少保存：

- `analysisTaskId`、`projectId`、`issueId`、`traceId`。
- 当时的 Bug 标题、描述、分析结论及相关文件。
- `repoCommit`、工作区是否有未提交变更、分析时间。
- Provider、模型配置、Prompt 模板版本或摘要、实际注入的经验 ID 与修订号。
- 日志引用及可获取的耗时、Token 用量；拿不到的用量记为未知，不记作零。

云端持久化输入和最终结论等必要快照；原始调查日志可保存在本地，通过任务 ID 关联，不强制上传完整源码和日志。代码版本在原分析时记录，不能等反馈到来后用当前版本代替。

原日志丢失、历史提交不可用或原工作区有未保存变更时，明确标记证据缺失。提交号不能还原未提交内容，不声称可以精确重放。需要历史代码时使用只读查看方式，不自动切换或重置正在使用的工作区。

### 5.2 原始反馈

`FeedbackRecord` 至少包含：

- `feedbackId`、平台事件去重标识、`analysisTaskId`、`projectId`。
- 评价、原因类别、补充说明、可选实际根因及证据引用。
- 反馈人、创建时间、可选 `supersedesFeedbackId`。
- 接收时是否允许自动提炼 `autoProcessEligible`，以及处理结果引用。

原始反馈是来源材料，不直接成为可信知识。

### 5.3 任务类型与路由

现有分析任务在演进后标识为 `analysis.run`，新增 `feedback.process`。两者共用任务生命周期，但使用不同业务负载。

任务信封包含 `taskId`、`type`、`projectId`、状态、重试次数、创建时间、领取者、租约信息和负载。反馈负载引用 `feedbackId`、原分析快照及反馈内容，不含任意执行指令。

新增稳定项目配置 `PROJECT_ID`，云端入口和 Worker 绑定同一标识。云端按绑定关系派发，不能只信任客户端随意提交的项目参数；本地目录仍由 `REPO_PATH` 决定。

任务生命周期：`queued → claimed → running → completed/failed`。租约过期可重入队；旧租约持有者不能覆盖新一轮执行结果。现有客户端和历史任务的迁移兼容需在阶段一实现时明确，不能静默跨项目领取。

### 5.4 反馈处理结果

处理结果与任务执行状态分开：

| 结果 | 含义 |
| --- | --- |
| `recorded_only` | 已落盘，无需提炼、功能关闭或缺少证据；附具体原因 |
| `candidate_created` | 已生成候选，尚未进入召回 |
| `manual_action_suggested` | 建议人工维护文档或 Skill，附建议位置、内容和依据 |
| `needs_confirmation` | 多方冲突或证据不足，需要补充或确认 |

同一反馈可以包含多个结果项，例如一条候选经验和一条文档维护建议。程序异常使用任务 `failed`，不混同于“没有足够证据形成经验”。

## 6. 持久化、重试与一致性

- 云端使用持久任务存储；反馈与对应任务应原子保存。不能先确认接收成功，再依赖易丢失的内存入队。
- 采用至少一次投递和幂等处理，不承诺端到端恰好一次。
- 平台事件去重、反馈落盘、候选生成分别使用稳定标识。重试先检查已有产物与内容摘要，复用已完成步骤，避免重复模型调用。
- 若模型调用完成但产物尚未持久化即崩溃，重试仍可能重复消耗 Token；记录尝试并受重试预算限制。
- 租约、续租、有界重试和最终失败状态覆盖 Worker 离线与进程中断。初版保持单 Worker 串行执行，Bug 分析优先于经验提炼。
- 文件由固定程序校验后原子替换；确认与索引重建串行处理。索引可重建，不作为唯一事实来源。
- 通知使用独立持久待发送记录。通知失败不重跑已完成的提炼；保存消息发送结果以尽量抑制重复，明确网络不确定窗口仍可能重复通知。
- 同一项目第一版绑定一个负责该工作区的 Worker；多机器经验同步不在首版范围。

## 7. 项目内文件组织

```text
<REPO_PATH>/.agent-memory/
  feedback/
    <feedbackId>.json
  candidates/
    <experienceId>.md
  experiences/
    <module>/
      <experienceId>-<short-slug>.md
  archive/
    <experienceId>/
      <revision>.md
  index.md
```

目录按稳定模块组织，跨模块匹配依靠元数据标签，不把每个关键词都做成目录。文件 ID 是稳定身份，名称只用于阅读。原始反馈和候选默认不进入普通分析的经验检索。

正式经验建议格式：

```markdown
---
id: EXP-001
revision: 1
status: confirmed
project_id: h5-project
module: account
tags: [账号切换, 缓存, 数据未刷新]
source_feedback_ids: [feedback-123]
source_analysis_task_id: task-123
observed_commit: <原分析提交>
confirmed_by: <确认人>
confirmed_at: <时间>
---

## 适用现象
切换账号后页面仍显示前一个账号的数据。

## 之前的错误
优先怀疑组件未重新渲染，未检查缓存隔离。

## 已确认的证据
记录人工反馈、相关文件和修复提交，区分已证实内容与假设。

## 下次优先检查
检查缓存键是否包含用户身份，以及切换账号时是否清理缓存。

## 适用边界
仅作为调查线索，确认当前版本是否仍使用该缓存机制。
```

示例只说明格式，不代表该项目已发生此问题。正式经验还应保存修订、替代和合并关系；代码路径是可变线索，来源 ID 和证据才用于追溯。

## 8. 提炼、人工确认与知识归属

提炼调用输入为原反馈、原分析快照、可用的相关日志、有限范围代码证据和相关既有经验。模型返回结构化候选及证据引用，固定程序验证后渲染文件，避免模型直接控制落盘路径。

每条候选必须回答：在什么可观察条件下适用、之前遗漏了什么、依据是什么、下次应检查什么、何时不适用。模型自述的高置信度不能代替证据。

优先寻找既有重复或冲突经验；生成修订、合并或停用建议，不自动覆盖正式条目。无法确认根因时可记录需要补充的问题，但不能把猜测写成正式教训。

| 内容 | 处理方式 |
| --- | --- |
| 个案误判、反例、特定条件下的检查提醒 | 生成候选经验，经人工确认后召回 |
| 稳定模块边界、业务事实、接口约定 | 通知建议人工补项目文档或模块 Skill |
| 多次验证有效的通用调查步骤 | 通知建议人工补 Skill 流程 |
| 偶发网络、格式或执行失败 | 保存运行记录，优先工程修复，不默认形成经验 |

第一版计划提供本地列出、查看、确认、拒绝、修订和停用的维护入口；具体命令尚未实现。维护入口校验元数据、保存确认人和时间，并同步重建索引。人工可以编辑候选正文，再通过入口确认；仅有候选文件不算生效。

人工补完文档或 Skill 后，可手动把关联经验标记为已合并并停用召回，保留来源和目标文档引用。系统不检查到建议后就自行修改这些文件。

## 9. 召回与使用

### 9.1 触发条件

召回依据任务特征，不依赖 Agent 是否承认分析失败。第一版在每次符合分析条件的源码调查前，由 Worker 固定执行一次检索，复用同一候选集合供 Provider 回退使用。

当前 Worker 已使用“通用模板 + 本地项目补充提示词”的统一组装流程，配置见 README 的“项目提示词配置”。经验召回实现时在该组装点增加独立的有界经验区段，不把经验写入本地项目补充文件。

检索输入包括项目标识、Bug 标题和描述中的症状、模块名、路径和标签词。起步检索不额外调用模型，不依赖尚未生成的根因结论。

形成初步结论后，利用模块、文件和根因假设再检索反例，作为后续扩展；首版不强制增加第二次 Agent 调用。

### 9.2 匹配与预算

- 只检索本项目、状态有效且已确认的条目。
- 采用模块、症状词、路径和标签的确定性匹配排序，中文匹配需通过真实样例验证，不仅依赖英文分词。
- 不足阈值时不强行返回；初始上限建议为 3 条，总注入摘要不超过 3,000 字符，实施时用案例校准。
- Prompt 注入经验 ID、修订号、适用条件、检查提醒和文件路径；Agent 可按需读取全文。
- 摘要不能挤掉原始 Bug 信息。索引缺失可重建；经验格式损坏或检索失败时记录原因并继续普通分析。
- 超出当前代码适用范围、互相冲突的经验不得被静默当作规则；显式提示当前事实复核。

### 9.3 使用记录

每次分析分别记录：被检索返回的经验、实际注入的经验、Agent 报告读取的经验、实际执行的检查以及采用或排除理由。Agent 自述与可观察工具日志区分保存，不把“已注入”当成“已采用”。

历史经验只能提示检查方向，结论仍需当前代码证据。无匹配时正常调查，不自动读取所有原始反馈。关闭功能时不通过本功能读取或注入经验；目标项目自身已有 Skill 若独立读取同类文件，不属于此开关可控制的范围。

## 10. 开关与成本控制

新增 Worker 环境变量 `EXPERIENCE_ENABLED`，默认 `true`；显式设置为 `false` 时关闭自动提炼与召回。该开关由 Worker 在启动时读取，修改后重启生效；非法值应报配置错误，避免误开启。配置仍使用 Bug Bot 仓库根目录 `.env`。

云端通过 Worker 能力上报获知项目开关状态。首次连接领取任务前上报，随后随轮询更新；云端不根据未知状态假定允许历史自动提炼。云端只调度，Worker 在真正调用模型前再次检查本地开关。

| 行为 | 开启 | 关闭 |
| --- | --- | --- |
| 普通 Bug 分析 | 保持原流程，增加有界经验检索 | 保持原流程 |
| 卡片反馈接收与云端保存 | 保留 | 保留 |
| 反馈任务领取与原始反馈落盘 | 执行 | 执行，不调用模型 |
| 经验提炼 | 符合条件且允许自动处理时执行 | 不执行 |
| 经验检索和注入 | 执行 | 不执行 |
| 已有经验文件 | 保留 | 保留 |
| 本地人工维护 | 可使用 | 可使用，不隐式调用模型 |

反馈接收时记录是否具备自动提炼资格：项目当时关闭或能力未知的反馈标记为仅记录，重新开启不自动批量补跑。领取时若 Worker 已关闭，则落盘并结束为 `recorded_only`，不会留在队列等待未来开启。历史补处理必须由人工明确发起，并保留原反馈 ID 和新的处理尝试。

首次能力上报前收到的反馈也不会在上线后自动消耗 Token。云端显示最近已知状态，不能把缓存状态描述为本地实时状态。

提炼使用有界输入、超时和重试预算；首版每次正常处理只做一次提炼调用，输出校验失败不进入无限自我修复。按任务类型记录模型调用、耗时及可获取的用量。即使检索本身不调用模型，注入上下文也会增加普通分析的 Token 成本。

## 11. 通知与写入边界

通知至少区分：已接收反馈、已生成候选待本地确认、建议人工维护文档或 Skill、仅记录及原因、处理失败。人工确认生效后由 Worker 回报状态，云端再通知；断网时保留待回报记录。

维护建议给出原因、建议文件和可审阅的文字，不暗示已经改动项目。候选通知给出经验 ID 和本地相对路径，不暴露本机绝对目录或完整敏感日志。

反馈文字和 Bug 内容均作为不可信数据，不成为命令或高优先级指令。固定程序限制写入 `.agent-memory/` 下预定路径，校验 ID、路径穿越和链接越界。模型输出通过结构校验后再写入；提炼过程只读调查，文件写入由宿主程序执行。

项目 Token 与任务授权必须阻止跨项目读取反馈或派发任务。相关反馈入口、卡片验证及实际 CLI 只读约束需在实施时验证，不能仅靠 Prompt 声明安全边界。

## 12. 分阶段实施与验收

### 阶段一：反馈与可靠落盘

实施反馈卡片、回调验证、分析快照、项目路由、持久任务、租约与幂等、Worker 原始反馈落盘及处理通知。不接入经验模型调用。

验收：

- 用户可反馈并追加更正；重复平台事件不产生重复记录。
- 云端重启或 Worker 暂时离线后，反馈及任务仍可恢复。
- 重复领取不重复落盘，错误项目 Worker 无法领取。
- 原分析与反馈可以通过 ID 关联；版本和证据缺失有明确标记。
- 通知失败可独立重试，不重新处理任务业务。

### 阶段二：候选提炼与人工确认

实施开关能力上报、提炼资格、结构化候选、人工维护建议、本地确认入口、经验修订与索引重建。

验收：

- 默认开启，显式关闭后不会触发经验相关模型调用；普通分析仍可运行。
- 关闭或能力未知时收到的反馈仍能保存，重新开启不自动补跑。
- 证据不足或多人反馈冲突时不自动生成已确认知识。
- 候选未经确认不可召回；确认、拒绝、停用和修订均可追溯。
- 文档和 Skill 建议只产生通知，不修改相关文件。
- 重试复用已落盘产物，输入及调用次数受预算限制。

### 阶段三：分析前召回与效果评估

实施确定性检索、摘要注入、经验使用记录、无匹配降级和历史案例回放。

验收：

- 即使 Agent 未认为自己失败，分析前仍执行检索。
- 只召回当前项目的有效正式经验，遵守数量和长度上限。
- 能展示一次有效召回，以及一次因当前代码证据不符而排除经验的案例。
- 检索异常不阻断普通分析，关闭开关不注入经验。
- 区分召回、采用和最终正确，不用曝光次数冒充效果。

评估使用人工确认案例，对比开启与关闭召回的根因正确率、错误确定性结论比例、耗时和 Token 成本。固定模型配置、Prompt 和 Bug 对应代码版本，按时间隔离经验来源与测试案例，避免同一问题的修复答案泄漏进测试上下文。报告样本量、未知项及波动，不预先承诺效果提升。

## 13. 首版暂不实施与后续触发条件

- 不自动修改项目文档和 Skill；此边界已确认，并非等待自动化的默认下一步。
- 不做云端经验审核 UI、多机器文件同步、自动 Git 提交或向量数据库。
- 不做依赖模型主观置信度的自动确认，也不根据一次成功自动提高经验可信度。
- 不默认补跑历史反馈或对所有正常分析额外做模型复核。
- 出现关键词检索明显漏召回后再评估语义检索；出现初次查询信息不足后再评估结论前第二次召回。
- 经验规模扩大或过期提醒增多时，再增加留存、衰减和维护策略。

后续实施需核实飞书卡片及回调协议、存储迁移细节和 CLI 执行约束，并据实际文档确定接口与配置；这些技术核实不改变本文已确认的产品边界。本轮到设计文档完成为止，实施需另行开始。
